## SUMMARY
## Architecture, hosting, LLM, Play Store and competitors: key conclusions

**Research limitation:** The shared web-search budget ran out after 3 searches. Those searches confirmed the GitHub Actions schedule and Pages limits and some Cloudflare free-tier numbers. Claude pricing comes from the bundled Anthropic API reference, cached 2026-10-06. Everything else is training knowledge and is labeled that way. Competitor prices, the 2026 Play target-API deadline and Play's gambling-policy wording are the facts most likely to be out of date, so check them before committing.

### Recommended architecture: "static-first, thin edge"
1. **Client:** Vite + TypeScript + Preact (or Svelte 5) as an installable app (PWA), using vite-plugin-pwa/Workbox in injectManifest mode. Store league data in IndexedDB with `idb` (or Dexie). Run Monte Carlo simulations in a Web Worker through Comlink. **Skip DuckDB-WASM at first.** The data is small (about 2k players × N sources × 18 weeks), so precomputed, compressed JSON shards plus plain JS (or Arquero) are enough. Adding DuckDB-WASM would mean several MB of downloads and a slow start for no real gain.
2. **Data pipeline:** Scheduled GitHub Actions jobs fetch, normalize and rescore consensus and projections, then publish versioned JSON plus a `manifest.json`. Scheduled jobs run at most every 5 minutes, and their timing isn't guaranteed: they can run 15–30+ minutes late under load. In a public repo they are disabled after 60 days without activity, which would hit you in the offseason. Use offset cron minutes (e.g. `7,37 * * * *`), a `workflow_dispatch` fallback, and optionally a Cloudflare Cron Trigger that fires `repository_dispatch` when timing matters (Sunday inactives).
3. **Where the data lives:** For the MVP, deploy app and data together with `actions/upload-pages-artifact` + `actions/deploy-pages`. That avoids the git-history bloat of committing JSON every hour. Pages serves `Access-Control-Allow-Origin: *` and a fixed 10-minute `Cache-Control` you can't change. Work around it with `fetch(url,{cache:'no-cache'})` (an ETag check) or content-hashed filenames. **For v1, move the data to Cloudflare R2** (10 GB free, no download fees, settable Cache-Control and CORS) behind a custom domain.
4. **Small backend (v1): one Cloudflare Worker** (free: 100k requests/day, about 10 ms CPU per request, and waiting on network calls doesn't count toward CPU). It handles:
   - the Claude API proxy (protected by Turnstile, with per-user quotas in D1 or a Durable Object)
   - a stateless ESPN cookie pass-through, locked to an allowlist of ESPN hosts
   - the Yahoo OAuth code exchange
   - later, verifying Play purchases

   Sleeper needs **no** backend: `api.sleeper.app/v1` is read-only, needs no login and allows browser calls (CORS). Avoid Vercel's free Hobby plan (non-commercial use only) and Supabase's free plan (projects pause after a week idle, which bites in the offseason).

### LLM (Claude)
Current prices per million tokens (cached 2026-10-06):

| Model | Input | Output | Cached input reads |
|---|---|---|---|
| Haiku 5.5 | $0.10 | $0.50 | – |
| Sonnet 5.5 | $2 | $10 | $0.20 |
| Opus 5.5 | $4 | $20 | $0.20 |

Haiku's price applies to prompts of 100K tokens or less. Writing to the prompt cache costs 1.25× the input price (5-minute TTL) or 2× (1-hour TTL). The Batch API is 50% off.

- **Cost per explanation:** about $0.001 on Haiku 5.5 and about $0.01–0.03 on Sonnet 5.5, counting the always-on thinking tokens.
- **Cost of "ask the analyst" chat:** about $0.05–0.15 per Sonnet session. A heavy user costs roughly $1–3/month on Sonnet, or cents on Haiku.

Three design rules:
- **Never put the key in the static app.** Anyone can read it from the bundle or the network tab.
- **Generate non-league-specific write-ups in the pipeline** with the Batch API, keeping the key as a GitHub Actions secret, so the cost is shared across all users.
- **Offer bring-your-own-key** using direct browser calls (`anthropic-dangerous-direct-browser-access: true`).

Ground the chat with tool use over the app's computed data (projection distributions, win probability, matchup grades), so the model explains numbers and never invents them.

### Google Play (TWA)
- **Tooling:** Use Bubblewrap or PWABuilder.
- **Hosting:** `assetlinks.json` must sit at the **origin root**. A `user.github.io/repo` project site can't provide that, so use a custom domain from day one (and add `.nojekyll`).
- **Timeline:** New personal developer accounts need a closed test with 12 testers for 14 days before going to production.
- **Target API:** It was API 35 by Aug 31 2025, and is probably API 36 for 2026 (unverified).
- **Billing:** Subscriptions use the Digital Goods API with Play Billing and need server-side purchase-token verification (the Worker).
- **Gambling policy:** An advice app isn't a gambling app. But **leave sportsbook links and affiliate offers out of the Play build**, and present betting lines as derived implied team totals.
- **Data safety form:** Declare league IDs, chat text sent to Anthropic, and ESPN cookies if they pass through the proxy.

**Legal issue to resolve first:** GitHub Pages' usage terms forbid using it mainly for commercial SaaS. Host the app shell on Cloudflare Pages/Workers static assets before charging anyone.

### Competitors and the gap you can own
- **FantasyPros** owns expert consensus rankings (ECR) plus league sync (My Playbook, Start/Sit, Trade Analyzer, Waiver Assistant), at roughly $4–15/month (unverified).
- **ESPN** has IBM watsonx trade and waiver grades.
- **PFF** has WR/CB matchup charts.
- **FantasyPoints** has man/zone coverage data.
- **Draft Sharks** has an Injury Predictor.
- **KeepTradeCut and FantasyCalc** offer free dynasty values.

Almost all of them rank players by average points and explain little. A solo dev can credibly own five things:
1. **Decisions based on your chance of winning.** Start/sit and trades judged by P(win this week) and season or playoff simulations, accounting for variance and the opponent's lineup.
2. **Exact custom scoring.** Every source's raw stat projections recalculated under your league's actual Sleeper rules (TE premium, superflex, bonuses).
3. **Open reasoning.** Showing where sources disagree, plus a public scorecard of how accurate past calls were.
4. **League-specific context.** Roster needs, how active league-mates are on waivers, FAAB spending.
5. **An analyst grounded in data.** An LLM chat that can only cite computed numbers.

Lead with Sleeper. It is free to integrate and its users play dynasty and custom formats the most.

### Net assessment
The infrastructure numbers in this report are largely trustworthy. GitHub Actions and Pages limits, the Pages commercial-use restriction, the Cloudflare Workers/KV/D1/R2 free tiers, Claude pricing, the BYOK header, Play's 12-tester/14-day rule and the API 36 target all match primary sources (official docs repos, the Anthropic SDK source, the bundled Anthropic skill). The Monte Carlo feasibility claim holds up in a real benchmark (50k matchup sims in about 36 ms; 10k 12-team seasons in about 0.3 s in V8). Treat these parts with caution in the plan: (1) ESPN is NOT CORS-blocked. Public leagues can be read client-side, and only private leagues need the proxy. The 'NFL.com migrated to ESPN for 2025' claim is unsupported; there was a non-binding Aug 2025 merger agreement, and its status for 2026 is unknown. (2) The recommended GitHub Pages deploy path (upload-pages-artifact v4+) silently drops /.well-known/assetlinks.json, which breaks the TWA unless you use v5's include-hidden-files. (3) Scheduled Actions can be dropped, not just delayed, so game-day refreshes need an external trigger and staleness detection. (4) The competitive analysis undersells FantasyPros: its prices run up to $22.99/mo, it has a paid LLM 'Coach AI' and a free 'Gameday Win %', so 'win probability' and 'AI analyst' are not differentiators on their own. Exact Sleeper-scoring rescoring, P(win) optimized against the actual opponent's lineup, and an open calibration ledger are. (5) The report misses Play's AI-generated-content policy (an in-app report/flag mechanism is required for the chat), Play's rule against using third-party APIs against their terms (relevant to the ESPN proxy and any scraped rankings), and the US alternative-billing programs with fees from Oct 1, 2026. The '500 Pages builds' argument for R2 is probably wrong for direct-upload deploys, though R2 for data is still a sound choice.

## FINDINGS
- [high LB] **GitHub Actions scheduling**: Scheduled (cron) workflows can run at most every 5 minutes, often run late under load (reports of 15-30+ min, worst at the top of the hour), and in public repos are auto-disabled after 60 days of no repository activity. — Sub-5-minute crons are accepted but not triggered. The 60-day auto-disable is in GitHub's official docs; activity (commits) resets it, and it is re-enabled manually from the Actions tab. The offseason (Feb-Aug) WILL trip this unless there is a keepalive or periodic commit. Mitigations: offset minutes (e.g. 7,37), workflow_dispatch for manual runs, and an external scheduler (Cloudflare Cron Trigger) calling the repository_dispatch REST endpoint (POST /repos/{owner}/{repo}/dispatches) for time-critical Sunday runs (inactives ~90 min before kickoff). (https://docs.github.com/en/actions/reference/usage-limits-billing-and-administration ; https://cronuru.com/guides/github-actions-scheduled-workflows ; https://runhooks.app/blog/github-actions-scheduled-workflows-unreliable/)
- [medium LB] **GitHub Actions minutes and job limits**: Standard GitHub-hosted runners are free and unmetered for public repos; private repos on the Free plan get 2,000 min/month (Pro 3,000). Jobs on GitHub-hosted runners time out after 6 hours, and each job is billed rounded up to the whole minute. — Example: a 2-minute hourly in-season job costs about 24*31*2 = 1,488 min/month, close to the private-repo Free cap once you add Sunday high-frequency runs. Recommended: a public repo for pipeline code (free minutes) with licensed or third-party data written to private storage (R2) rather than committed publicly. Actions secrets are not exposed to fork PR workflows. Late-2025 GitHub pricing changes (hosted-runner price cuts, a proposed self-hosted platform fee) did not change free public-repo usage as far as known; verify. (training knowledge)
- [high LB] **GitHub Pages limits**: A published Pages site may be at most 1 GB (hard limit); bandwidth has a 100 GB/month soft limit; the 10 builds/hour soft limit does not apply when deploying via a custom GitHub Actions workflow; excess traffic can get HTTP 429. — Source repos are recommended under 1 GB, and git blocks files over 100 MB. For hourly data publishing, use actions/upload-pages-artifact + actions/deploy-pages (each deploy replaces the whole site, with no git-history bloat) rather than committing JSON to a gh-pages branch, which grows the repo forever. GitHub suggests putting a CDN in front if quotas are exceeded. (https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [medium LB] **GitHub Pages headers / CORS / caching**: GitHub Pages responses include Access-Control-Allow-Origin: * and a fixed Cache-Control: max-age=600 that cannot be customized; ETag/Last-Modified revalidation works. — Cross-origin fetches of data JSON from another *.github.io site or a custom domain work without a proxy. Freshness: browsers may serve copies up to 10 minutes old. Use fetch(url, {cache: 'no-cache'}) on a small manifest.json (a conditional request) that points to content-hashed data files, which can be cached long-term. Custom headers (CSP, COOP/COEP for SharedArrayBuffer/multithreaded WASM) are NOT possible on Pages, which rules out multithreaded DuckDB-WASM there. (training knowledge)
- [medium] **raw.githubusercontent.com and release assets**: raw.githubusercontent.com sends ACAO: * but serves text/plain, has short caching, and has been increasingly rate-limited for unauthenticated traffic; GitHub Release asset downloads redirect to objects.githubusercontent.com and are not reliably CORS-fetchable from browsers. — Do not use raw.githubusercontent.com or release assets as the production data CDN for a browser app. Use Pages, R2 (custom domain), or Cloudflare static assets. (training knowledge)
- [medium LB] **GitHub Pages terms of use**: GitHub's Pages usage restrictions say Pages is not intended or allowed as free hosting for an online business, e-commerce site, or a site primarily providing commercial SaaS. — A free or ad-light hobby PWA is fine. A subscription product hosted on github.io is a terms-of-service risk. Plan to move the app shell to Cloudflare Pages/Workers static assets (unlimited static bandwidth on free) before adding paid tiers. Use a custom domain from day one so the move is invisible and Digital Asset Links stay stable. (training knowledge)
- [medium LB] **Cloudflare Workers free tier**: Workers Free: 100,000 requests/day (resets 00:00 UTC), ~10 ms CPU per invocation, 50 external subrequests and 1,000 Cloudflare-service subrequests per invocation. Paid is $5/month with 10M requests and 30M CPU-ms included and much higher CPU limits. — CPU time excludes time waiting on fetch(), so streaming a Claude response or proxying ESPN fits easily within 10 ms CPU. A blog claimed 30 ms CPU for free; the official limits page was not retrievable, so treat 10 ms as the conservative figure. Workers has a Rate Limiting binding and Turnstile (free bot challenge) for abuse control. Cron Triggers are available on free (a small number per account), useful as a reliable scheduler. (https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/index.md ; https://eastondev.com/blog/ja/posts/dev/20260526-cloudflare-free-limits/)
- [medium LB] **Cloudflare KV / D1 / R2 / Pages free limits**: KV free: 100k reads/day, 1k writes/day, 1 GB. D1 free: 5M rows read/day, 100k rows written/day, 5 GB. R2 free: 10 GB-month, 1M Class A, 10M Class B ops/month, no download (egress) fees. Pages free: unlimited static bandwidth, 500 builds/month, 20k files/site, 25 MiB max file size, custom headers via _headers. — KV's 1k writes/day makes it unsuitable for per-request LLM quota counters at scale. Use D1 or a SQLite-backed Durable Object for quotas and entitlements. R2 is the best target for hourly data publishing from Actions (S3-compatible API via aws-cli or wrangler): settable Cache-Control and CORS. Use a custom domain, not the rate-limited r2.dev URL. Hourly Pages deploys (~744/month) would exceed Pages' 500 builds/month, another reason to split the app (Pages) from data (R2). The R2 numbers in search came from a blog; KV and D1 numbers are from training. (training knowledge; R2 figures corroborated by https://eastondev.com/blog/ja/posts/dev/20260526-cloudflare-free-limits/)

Supabase is worth it only if you want hosted auth plus Postgres, and its pausing hurts in the offseason. Exact Netlify and Deno numbers are uncertain. (training knowledge)
- [high LB] **Sleeper API (client-side import)**: Sleeper's public API (https://api.sleeper.app/v1) is read-only, needs no authentication, allows browser calls (CORS), and asks clients to stay under ~1,000 calls/minute to avoid IP blocks. — Key endpoints: GET /user/{username}; /user/{user_id}/leagues/nfl/{season}; /league/{league_id} (includes scoring_settings, roster_positions, settings.waiver_budget); /league/{id}/rosters; /league/{id}/users; /league/{id}/matchups/{week}; /league/{id}/transactions/{round}; /league/{id}/traded_picks; /state/nfl; /players/nfl (~5 MB, fetch at most daily, ideally in the pipeline and trimmed); /players/nfl/trending/{add|drop}?lookback_hours=24&limit=25. - [medium LB] **ESPN private leagues**: ESPN's fantasy API (lm-api-reads.fantasy.espn.com/apis/v3/games/ffl/seasons/{year}/segments/0/leagues/{leagueId}?view=mTeam&view=mRoster&view=mMatchup&view=mSettings) sends no CORS headers and requires the espn_s2 and SWID cookies for private leagues, so a proxy is mandatory. — espn_s2 is a long-lived session credential (on the order of a year) for the user's whole ESPN account. Proxy design:
- stateless pass-through: the client sends the cookies in custom headers over HTTPS, the Worker sets the Cookie header, forwards, and returns.
- never log or persist the cookies; strip them from error reports.
- hard allowlist of the ESPN host and path prefix (no open proxy/SSRF).
- CORS restricted to the app origin; per-IP rate limit.
- the client stores the cookies only in IndexedDB, with a 'forget credentials' button and clear consent copy.
This is undocumented and unofficial (ToS gray area) and the API can change without notice (it moved hosts in 2024). Note: NFL.com Fantasy users were reportedly migrated to ESPN for 2025, which raises ESPN's priority. (training knowledge)
- [medium] **Yahoo Fantasy API**: Yahoo Fantasy Sports API (https://fantasysports.yahooapis.com/fantasy/v2/) uses OAuth 2.0 authorization code flow via api.login.yahoo.com; the token exchange needs the client_secret, access tokens last ~1 hour with refresh tokens, and the API has no browser CORS, so a Worker is required. — The Worker handles /oauth/callback (code to token exchange, client_secret held as a Worker secret) and either proxies API calls or returns tokens to the client. Default responses are XML (append ?format=json). Redirect URIs must be HTTPS. Whether Yahoo supports PKCE without a secret is unverified. (training knowledge)
- [medium] **Client stack**: For a solo dev, Vite + TypeScript + Preact (~4 KB gz core, plus Signals) or Svelte 5 (compiled, small runtime), with vite-plugin-pwa (Workbox 7, injectManifest), idb (~1 KB) or Dexie for IndexedDB, and Comlink (~1 KB) for Web Worker RPC, gives a small fast PWA. — Service worker strategy:
- precache the app shell
- stale-while-revalidate for data shards keyed by a content-hashed manifest
- network-only for Sleeper live endpoints, with an IndexedDB fallback for offline
Persist the league snapshot plus scoring_settings in IndexedDB. Ask for navigator.storage.persist() to reduce eviction (iOS Safari can evict storage for sites not added to the home screen). (training knowledge)
- [medium] **In-browser analytics: DuckDB-WASM vs Arquero vs JSON**: DuckDB-WASM costs several MB of WASM (exact compressed size varies by build; uncertain) plus startup latency, and its multithreaded build needs COOP/COEP headers that GitHub Pages cannot set; Arquero is a much smaller JS dataframe library; precomputed JSON shards are the lightest option. — Data volume is tiny (about 2,000 players × ~10-20 sources × weekly projection fields, well under 1 MB/week compressed). Precompute in the pipeline: consensus, distributions (mean/sd/percentiles per stat), matchup grades. Ship per-week/per-position JSON (Brotli-compressed by the CDN). Rescoring for custom league settings is a cheap dot product in JS. Revisit DuckDB-WASM only for a power-user 'research' tab over historical play-by-play. (training knowledge)
- [medium LB] **Monte Carlo in Web Workers**: Win-probability simulation (10k-50k draws of correlated player outcomes for two lineups) runs in well under a second in a Web Worker; full-season and playoff-odds sims for a 12-team league are also feasible client-side. — Model each player's fantasy points as a distribution: a skewed or lognormal-ish distribution, or a mixture with an injury/bust component, fitted from the projection spread across sources plus historical error by position. Add correlation for QB-WR stacks, same-team players, and game script. Start/sit decision = maximize P(my score > opponent score), not mean points. This difference from FantasyPros-style rankings is the core product edge. Use typed arrays and a seeded PRNG for reproducible explanations. (training knowledge)

## RECOMMENDATIONS
- [MVP] Build the client with Vite + TypeScript + Preact (or Svelte 5) + vite-plugin-pwa (Workbox injectManifest) + idb/Dexie + Comlink Web Worker; register a custom domain on day one. — Smallest bundle and simplest mental model for a solo JS dev. A custom domain keeps assetlinks.json at the origin root and lets you move hosting (GitHub Pages to Cloudflare) without breaking users or the TWA.
- [MVP] Import Sleeper leagues 100% client-side from api.sleeper.app/v1 (user to leagues to league/rosters/users/matchups/transactions), caching in IndexedDB; precompute a trimmed players file in the pipeline instead of having each client download the ~5 MB /players/nfl. — Sleeper has CORS, no auth and generous rate limits, so the MVP needs no backend at all.
- [MVP] Data pipeline in GitHub Actions (public repo): offset crons (hourly in-season, e.g. every 15 minutes Sunday 10:00-13:30 ET for inactives), workflow_dispatch, a keepalive for the 60-day disable; publish content-hashed JSON shards plus manifest.json via actions/deploy-pages; clients fetch the manifest with cache:'no-cache'. — Free, version-controlled, no servers. Content-hashed shards work around Pages' fixed 10-minute caching and avoid git-history bloat.
- [MVP] Ship the core edge first: per-player outcome distributions (spread across sources plus historical error), custom-scoring rescoring, and a Monte Carlo win-probability start/sit in a Web Worker, with deterministic templated explanations (no LLM yet). — This is the differentiation and costs nothing to run. The LLM is a presentation layer on top of these numbers, not the engine.

## RISKS
- [medium] Scheduled GitHub Actions runs are late or skipped at peak times (e.g. Sunday inactives), or silently disabled after 60 days of offseason inactivity. — mitigation: Offset cron minutes; a Cloudflare Cron Trigger firing repository_dispatch as the primary scheduler for time-critical windows; a keepalive workflow; client-side live polling of Sleeper injury status as a fallback; a 'data as of' timestamp in the UI.
- [medium] GitHub Pages terms disallow primarily commercial SaaS use, which would force a migration once subscriptions launch. — mitigation: Custom domain from day one; move the app shell to Cloudflare Pages or Workers static assets and the data to R2 before monetizing.
- [high] Data licensing and ToS: aggregating and republishing expert rankings or projections (FantasyPros ECR, PFF, KTC) or using undocumented APIs (Sleeper projections, ESPN) can bring cease-and-desists or sudden breakage. — mitigation: Prefer licensed or partner APIs and open data (nflverse); publish only derived outputs; keep raw third-party data private; isolate each source behind an adapter with health checks so one break doesn't take down the app.
- [medium] LLM abuse or cost blowup (scripted use of the hosted proxy, long chats on expensive models). — mitigation: Turnstile, per-user and per-IP daily token budgets in D1 or a Durable Object, Haiku 5.5 default, max_tokens and turn caps, prompt caching, a BYOK tier for power users, and spend alerts in the Anthropic Console.
- [medium] LLM states wrong facts (wrong injury, wrong opponent), damaging trust in advice. — mitigation: Tool-use grounding: the model may only cite tool outputs; include data timestamps; validate with structured outputs; show the underlying numbers next to the prose; never let the LLM make the decision.
- [medium] Handling ESPN espn_s2/SWID cookies (full-account session credentials) creates security and liability exposure. — mitigation: Stateless pass-through only, no logging or persistence, host allowlist, app-origin CORS, client-side storage with a delete option, clear consent text; consider importing a snapshot once rather than holding the credential continuously.
- [medium] Play Store delays or rejection: 12-tester/14-day closed test for new personal accounts, target-API deadlines, Data safety mismatches, gambling-policy misclassification if odds or sportsbook links appear. — mitigation: Start closed testing early; keep the Play build free of sportsbook links and promos; present odds as implied totals; keep the privacy policy and Data safety form in sync with actual data flows; pin targetSdk to the current requirement.
- [medium] Incumbents (FantasyPros, ESPN/IBM, Sleeper) ship similar AI and win-probability features, shrinking the gap. — mitigation: Compete on openness (calibration page), exact custom-scoring and league-specific modeling, and speed of iteration in the Sleeper/dynasty niche, rather than on breadth of content.
- [low] Stale research: competitor pricing, the 2026 Play target API, and Cloudflare free-tier numbers were mostly not verified this session (search budget exhausted). — mitigation: Verify on official pricing and limits pages before final plan sign-off; read limits at build time and design with headroom.
